## §1 — Purpose

Before authoring the full invitation pipeline (CMD-ACCORD-INVITATION-PIPELINE-1),
we need to confirm two things:

1. **Work Queue extensibility** — can a new request type (`accord_meeting_invitation`)
   be added to the existing `workflow_requests` / `workflow_instances` substrate
   without schema migrations, or does it require new tables?

2. **Cadence email mechanism** — how does the external email signoff work in
   Cadence (approve.html pattern), and can it be reused for meeting invitations
   without modification?

This commission answers both questions by reading existing code and substrate —
no writing, no deploying.

## §2 — Investigation A: Work Queue substrate

### A1 — `workflow_requests` table structure

```sql
SELECT column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_name = 'workflow_requests'
ORDER BY ordinal_position;
```

Key columns to identify:
- What `role` values exist? (This is the request type discriminator)
- Is there a free-form `body` / `metadata` column for arbitrary payload?
- Does `instance_id` FK to `workflow_instances` — or can it be NULL for standalone requests?

### A2 — `workflow_instances` table structure

```sql
SELECT column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_name = 'workflow_instances'
ORDER BY ordinal_position;
```

Key columns to identify:
- `workflow_template_id` — is this required? Can a meeting invitation be
  a standalone instance without a Cadence form template?
- `form_driven` — boolean flag. What happens when false?
- `submitted_by_resource_id` — is this the organizer (Vaughn) for meeting invites?
- `current_step_name` — what step names does the expense report flow use?
  Can we reuse `Review` → `Approved` / `Declined` for meeting RSVP?

### A3 — Existing `role` values in `workflow_requests`

```sql
SELECT DISTINCT role, COUNT(*) as count
FROM workflow_requests
WHERE firm_id = 'aaaaaaaa-0001-0001-0001-000000000001'
GROUP BY role
ORDER BY count DESC;
```

This shows what request types already exist. We need to determine whether
`accord_meeting_invitation` can be added as a new `role` value or whether
the column has a CHECK constraint limiting values.

### A4 — CHECK constraints on `workflow_requests`

```sql
SELECT conname, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'workflow_requests'::regclass
AND contype = 'c';
```

If `role` has a CHECK constraint, adding a new value requires a migration.
If it's a free `text` column, no migration needed.

### A5 — `workflow_requests` consumer in `mw-core.js`

Inspect `mw-core.js` lines 50 and 230 (identified in pre-read):
```javascript
// Line 50: Work Queue query
API.get(`workflow_requests?select=id,title,body,status,role,...`)
```

**Questions to answer from reading the consumer:**
- Does `mw-core.js` filter by specific `role` values, or does it render
  all open requests generically?
- If generic: a new `role='accord_meeting_invitation'` row would automatically
  appear in My Dashboard → Work Queue → Requests tab with no code changes.
- If role-specific: `mw-core.js` needs an amendment to render the new type.

### A6 — `workflow_requests` render path

Find where `_myRequests` is rendered in `mw-core.js` (around line 847 — the
`.myr-pt-steps` CSS suggests a step-progress UI). Determine:
- Is each request rendered with a generic template (title + body + accept/decline)?
- Or does each `role` have a custom renderer?

## §3 — Investigation B: Cadence email mechanism

### B1 — Locate `approve.html`

`mw-core.js` line 1551 references `approve.html` for external signoff.
Locate the file in the project. If not in uploads, ask operator to provide it.

**Questions to answer:**
- What URL parameters does `approve.html` accept? (token, instance_id, action?)
- Does it require a Supabase session (authenticated), or is it token-only?
- What does it write back when the external user approves/declines?
  (Which table, which column, which value?)
- Is the approval token generated by a Supabase Edge Function, a database
  trigger, or application code?

### B2 — Token generation pattern

Find where approval tokens are generated for the expense report / PTO flow.
Search for: `token`, `sign_url`, `approval_url`, `pg_net`, `edge function`,
`resend`, `sendgrid` in the Cadence CDN files or any email-related file.

**Questions to answer:**
- Is email sent via a Supabase Edge Function (`supabase/functions/`)?
- Or via a database trigger + `pg_net` HTTP extension?
- Or via application code in `cdn-*.js`?
- What email service is used (Resend, SendGrid, Mailgun, other)?

### B3 — External user experience

Trace the full flow for an external expense report approver:
1. Where does the email come from — what triggers the send?
2. What does the email body contain?
3. What URL does the "Approve" button point to?
4. What does `approve.html` do when the external user clicks?
5. What happens in the system after approval — which table updates?

### B4 — Reusability assessment

After tracing the flow, answer:
- Can `approve.html` accept a new `action_type=meeting_rsvp` parameter and
  write to `accord_meeting_attendees.rsvp_status` instead of a workflow step?
- Or does it need a separate `meeting-rsvp.html` page?
- Is the token generation generic (any entity_id + action) or tightly coupled
  to Cadence workflow instances?
